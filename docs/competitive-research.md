## 0. 调研口径

本插件要解决的不是「存菜谱」，而是 **「依据身体数据 + 权威膳食指南 + 节气 + 地域气候，持续生成不重样的多周期食谱，并执行到采购」**。因此竞品范围划为五类，而非只看同类「食谱 App」：

1. 自托管食谱管理与周计划（产品基准）
2. 中文菜谱库及其 AI/MCP 衍生生态（数据与中文场景）
3. 中文 AI 饮食助手（节气、中医养生、身体数据）
4. 营养与食材成分数据源（合规可复用的数据基础）
5. 插件 / 扩展形态（决定「插件」如何被分发与集成）

**已有资产**：本工作区 `diet-plan/` 已有一套可运行的五级计划体系（年/季/月/周/日 + 节气精确缓存 + 身体数据版本 + 去重台账 + 采购计划 + 上下层反馈闭环）。本插件的定位是**把这套 Markdown 驱动的方法论产品化、插件化、开源化**，而非从零造一个菜谱库。这一资产是差异化的实证基础，见 §5。

| 项目 | 技术栈 | 亮点 | 局限 | 许可证 |

## 4. 竞品共性缺口（机会点）

1. **「存菜谱」与「开处方」错位**：A 层让人手动排菜再统计营养；本插件应先由身体数据推出量化处方，再让菜单满足处方（约束求解方向相反）。
2. **周期粒度单一**：主流只到「周」；无年/季/月框架，导致节气主线、阶段目标、跨月周归属无法表达。
3. **去重是事后过滤而非台账治理**：仅 HealthRecipe 有 14 天窗口；缺少「最近 7 天组合不重样 + 近 4 周主菜重合上限 + 允许按节气/年度周期性重复」的分级规则。
4. **层级一致性无人处理**：多周期必然产生「上级框架变更 / 下级发现上级错误」的冲突，现有项目均无反馈台账、修订标注、时间线护栏。
5. **本地化停留在「节气建议」**：没有把「精确交节时刻 + 城市气候带 + 本地时令食材 + 本地采购渠道」串成可变量化、可变更的数据链路；搬家/体测后无法自动重算。
6. **采购止于清单**：缺分批采购日、易腐/耐储、缺货等价替换、剩余执行窗口折算（周中补跑不照搬全周量）。
7. **社区与合规薄弱**：多个中文小项目缺 LICENSE / CONTRIBUTING / SECURITY；MCP 衍生项目出现 README 与 npm 许可证冲突；菜谱爬虫数据有版权隐患。

## 5. 差异化定位

> **一句话**：不是又一个菜谱库，而是**「以《中国居民膳食指南》为约束、以身体数据为处方、以节气与地域为时令、以 Markdown 为单一数据源的多周期食谱规划引擎 + 可嵌入插件」**。

四个护城河（均已在 `diet-plan/` 中跑通，可直接产品化）：

| 护城河 | 现状可复用资产 |
|--------|----------------|
| 五级周期治理 | `2026-annual.md` / `2026-Q4.md` / `2026-11-month.md` / `2026-W45-week.md` / `2026-11-07-daily.md` + `_schedule.md` |
| 动态数据版本化 | `_profile.md`（身体/处方/居住地/节气四版本）、`_changelog.md`、节气联网缓存 `_data/solar-terms-YYYY.md` |
| 去重与反馈闭环 | `_history.md`（去重台账）、`_feedback.md`（A/B/C 上行 + D 类上级下发 + 时间线护栏） |
| 可执行性 | 周采购计划（品类汇总/分批/替换/深圳渠道/预算）、日前夜备餐清单、ATDD 式验收对照表 |

**目标用户**：① 有减脂/保肌目标、愿意记录体测数据的中文用户；② 用 AI Agent / 纯文本工作流的开发者（MCP、Skill、CLI）；③ 关注隐私、拒绝把身体数据上传 SaaS 的自托管用户。

## 6. 对规格（SPEC.md）的约束

由调研结果导出的**必须写入规格**的约束：

| 编号 | 约束 | 来源依据 |
|------|------|----------|
| C-01 | 营养计算必须**先处方后菜单**，且热量不得低于 BMR、蛋白设下限 | A 层「事后统计」缺陷、C 层无处方 |
| C-02 | 必须支持年/季/月/周/日五级，且允许年/季节气性重复、禁止日级短期重复 | §4-2 / HealthRecipe 14 天窗口 |
| C-03 | 节气必须用**当年精确交节时刻**并联网下载缓存，禁止内置近似表 | 已实测近似表偏移一天（雨水 2/18、芒种 6/5） |
| C-04 | 居住地与身体数据为**可变档案 + 版本号**，变更触发重算 | §4-5；AI_Diet_Assistant 天气模块仅实时、无版本治理 |
| C-05 | 上下层冲突需分级、留痕；**已执行计划不得回改** | §4-4；现有竞品全缺 |
| C-06 | 采购计划需含分批、缺货等价替换、剩余窗口折算 | KitchenOwl / Mealie 仅到清单 |
| C-07 | 菜谱与营养数据源必须**可插拔且许可证可审计**；默认源须为公有领域或明确开放许可 | HowToCook-mcp 许可证冲突、成分表 OCR 版权风险 |
| C-08 | 全仓库包含完整 GitHub 社区规范文件；许可证与第三方数据许可须显式声明 | §4-7 |
| C-09 | 输出为**纯本地 Markdown/结构化文本**，离线可用、身体数据不出本机 | 隐私优先，区别于 SaaS AI 助手 |
| C-10 | 健康声明与免责：非医疗处方；不得复制膳食指南原文/图表 | 出版物版权 + 健康合规 |

## 7. 形态对比与推荐（供 Clarify 阶段确认）

**推荐主形态：Markdown-first 核心库 + CLI + MCP Server（可插拔适配层）**，理由：

- 与已有 `diet-plan/` 资产同构（纯文本、Git 可追踪、零服务），迁移成本最低；
- MCP 一次实现即可覆盖 Claude / Cursor / VS Code / Copilot 等，中文菜谱生态已验证该分发路径；
- CLI 让 SDD/ATDD 的验收场景能直接在 CI 中执行（Given/When/Then → 命令 → 断言文件）；
- 避免 A 层的自托管 Web 重部署，保持「插件」定位。

**可选次级适配层**（后续阶段，不进 v1）：Agent Skill 包、Obsidian / VS Code 扩展、静态站点导出。

⚠️ **待用户确认**：目标宿主平台（MCP / Skill / 编辑器扩展 / Web）、实现语言（TypeScript / Python）、许可证（MIT / Apache-2.0 / GPL-3.0）。这些将作为 `SPEC.md` 的 `[NEEDS CLARIFICATION]` 项，不在此阶段臆定。

| 《中国食物成分表》OCR 数据版权与准确性 | 高 | 默认不打包；改为可插拔适配器 + 用户自备数据；优先 CC0 的 USDA FDC，并对中国食材做人工校验子集 |

## 9. 结论

市场在「存菜谱 + 周计划 + 购物清单」已高度成熟（Mealie / Tandoor / KitchenOwl），中文 AI 饮食助手也各自实现了节气、天气、忌口、14 天去重等单点能力，**但没有任何项目把「量化营养处方 → 五级周期治理 → 时令/地域 → 去重台账 → 采购执行 → 上下层反馈闭环」串成一条完整链路**。这既是空白，也正好是 `diet-plan/` 已验证资产的直接产品化路径。

建议以 **§7 推荐形态** 进入 SDD 的 Specify 阶段，规格须满足 §6 的 C-01～C-10 全部约束，并把 §7 的待确认项显式列入澄清清单。
