## 3. ADR-002 · 实现语言：机械语言可行性与 ISO 标准化语言选型

| 项 | 内容 |
|----|------|
| 状态 | **Accepted**（用户 2026-11-06 授权：「可以使用机械语言吗，如不行，使用 ISO 指定的语言」） |
| 决策者 | 用户（提出约束） + 本项目（在授权范围内完成选型与取证） |
| 影响 | 关闭 CL-02；决定 `plan.md` 技术栈、目录结构、CI 矩阵与 GPL 源码义务的实现方式 |
| 不改变 | 任何 FR / AC / SC 的业务语义；FR-041 / P-11 的 Canonical ID 内部表示约束保持不变 |

### 3.1 背景

用户原话「**搭建语言使用计算机标准语言，输出语言为用户指定语言**」。后半句已由 D-05 关闭。前半句在 2026-11-06 追问中进一步明确为条件式约束：**优先考察机械语言；若不可行，则采用 ISO 指定的语言**。

原表述的三种可能口径及归属：

| # | 可能含义 | 归属 |
|---|----------|------|
| 1 | **实现语言**采用某种有正式标准的编程语言 | 本 ADR 关闭 |
| 2 | **内部构建表示**采用与自然语言解耦的机器标准标识 | 已独立固化为 FR-041 / P-11，无需二选一，不受本 ADR 影响 |
| 3 | 两者兼指 | 第 1 项按本 ADR，第 2 项保持不变 |

**术语边界**（避免歧义影响结论）：

- **机械语言 / machine language**：处理器直接执行的二进制指令编码（ISA 级），不是可移植的程序源码。
- **汇编 / assembly**：机器指令的符号化表示，仍绑定具体 ISA 且缺少标准库；本 ADR 中结论相同。
- **形式化规格语言**（TLA+ / Z / B 等）：用于写规格与验证，不是运行时实现语言；若用户原意为此，可作为可选的验证工具，但**不能**替代实现语言，也不改变本决策。
- **ISO 指定的语言**：由 ISO/IEC 发布的、状态为 **Published / 现行**的编程语言国际标准所规范的语言。已撤销（Withdrawn）的标准不计入。

### 3.2 决策驱动

| # | 约束来源 | 要求 |
|---|----------|------|
| D1 | 用户 CL-02 | 实现语言须「计算机标准」；机械语言不可行时用 ISO 指定语言 |
| D2 | FR-030 / CL-01 | MUST 提供 MCP Server，优先官方 SDK 生态 |
| D3 | NFR-004 | Windows / macOS / Linux 三平台均可运行核心 CLI |
| D4 | FR-037 / GPL-3.0 | 必须提供 **Corresponding Source**（可修改的首选形式） |
| D5 | P-02 / P-03 / FR-038 | ATDD 红→绿、CI、lint、规格一致性、可审查可 diff |
| D6 | FR-040～046 / NFR-001 | 七语言（含拉丁语）UTF-8、离线、语言与逻辑解耦 |
| D7 | FR-052 | v1 仅 GitHub Releases + 源码，不发包管理器（不要求运行时零安装，但不得引入发布流水线） |

### 3.3 机械语言可行性评估 → ❌ 不采用

| 维度 | 判定 | 理由 |
|------|------|------|
| **平台可移植** | ❌ | 机器语言与 ISA 绑定（x86-64 / ARM64 / RISC-V 互不兼容），违反 NFR-004；每个平台需单独产物与维护链 |
| **必需抽象** | ❌ | 没有 UTF-8 字符串、JSON、文件系统、日期/时区、正则、进程 I/O 等标准抽象。FR-030 的 MCP JSON-RPC over stdio、FR-040～046 的七语言渲染、§6.5 采购清单全部要从零手写 |
| **许可证合规（决定性）** | ❌ | GPL-3.0 以「**source code = preferred form of the work for making modifications to it**」定义源码，并在分发非源码形态时要求随附 **Corresponding Source**。纯机器码不是可修改的首选形式 → **无法满足 GPL-3.0 的源码义务**（FR-037） |
| **SDD / ATDD** | ❌ | AC-01～19 要求可读、可 diff、可 lint、可测试的契约实现；覆盖率、CI 门禁、社区 PR（US-10）无落点 |
| **供应链与维护** | ❌ | 无法审计依赖许可、无法方便地打安全补丁，与 FR-053 静态扫描门禁、SECURITY.md 冲突 |
| **可贡献性** | ❌ | GPL 开源项目若没有人类可修改源码，社区协作与 fork 实质失效 |

> 结论：**机械语言不是「搭建语言」的可行选项**。汇编同理（仅可作为某一平台的极小适配层，不能作为主实现）。因此按用户授权，回退到「ISO 指定的语言」。

### 3.4 ISO 标准化语言候选（2026-11-06 联网核实）

| 语言 | ISO/IEC 标准 | 标准状态 | MCP 官方 SDK | 结论 |
|------|--------------|----------|--------------|------|
| **ECMAScript** | **ISO/IEC 22275:2018** — *ECMAScript® Specification Suite*；语言文本由 **ECMA-262** 年度维护 | ✅ **Published，2025 年复核确认现行**（ISO 官网 stage 90.93） | ✅ **Tier 1**（`@modelcontextprotocol/sdk`，TypeScript SDK，JS 可直接调用） | ✅ **采用** |
| C++ | ISO/IEC 14882:2024（:2011 / :2017 已撤销） | ✅ 现行 | ❌ 无官方 SDK | 备选 B：标准最「正统」，但需自实现 JSON-RPC / stdio 与 i18n，且引入第三方 JSON / ICU 依赖，与 D5 快速迭代、NFR-008 供应链审计相悖 |
| C | ISO/IEC 9899 系列 | ✅ 现行 | ❌ | 不选：抽象层级更低 |
| C# | ISO/IEC 23270:2018 | ❌ **Withdrawn（已撤销）**，且 ISO 版本滞后于现行语言 | ✅ Tier 1 | 不选：不满足「现行 ISO 指定」 |
| Ruby | ISO/IEC 30170 | 覆盖有限 | Tier 3 | 不选 |
| Python / Go / Rust / Java / Swift / Kotlin / PHP | **无 ISO 编程语言标准**（事实标准或厂商规范） | — | 部分 Tier 1/2 | 不选：不符合 D1 硬约束。**上一轮推荐的「Python 备选」因此作废** |

**两个易错点（已核实）**：

1. 常被引用的 **ISO/IEC 16262:2011**（ECMAScript 5.1）已于 **2018-05-09 撤销**，由 **ISO/IEC 22275:2018** 取代。22275 定义「规范套件」，套件本身不随组件年度版变化，并在 2025 年复核确认现行 —— 因此引用 ISO 编号时**必须写 22275:2018**，不可再写 16262。
2. **TypeScript 没有独立 ISO 编号**（它是 ECMAScript 的类型化超集，由 ECMA-262 之外维护）。若本仓库源码写成 `.ts`，严格意义上「实现语言」就不再是 ISO 指定语言。故采用**纯 ECMAScript 源码**；MCP SDK 是第三方依赖库而非本项目实现源码，其自身使用 TS 不影响本仓库主实现语言口径。

### 3.5 决策

| 项 | 选定值 |
|----|--------|
| **实现语言** | **ECMAScript**，依据 **ISO/IEC 22275:2018**（ECMAScript® Specification Suite，现行），语言特性遵循 **ECMA-262 现行版** |
| **源码形态** | 纯 **ESM JavaScript**（`.js`，`"type": "module"`），UTF-8 文本，人类可读可修改；**仓库不含 `.ts` 实现源码** |
| **运行时** | **Node.js 20 LTS 及以上**（Windows / macOS / Linux）；核心仅依赖 Node 内置模块（`node:fs`、`node:path`、`node:test`、`node:assert`、`Intl`） |
| **MCP 适配** | 官方 Tier 1 SDK `@modelcontextprotocol/sdk` + **stdio transport**；其许可在 M4 `THIRD_PARTY_NOTICES.md` 审计，冲突则不引入 |
| **国际化** | `Intl`（ECMA-402）仅用于日期 / 数字 / 单位格式化；**词汇翻译全部来自本地语言包**（FR-041），不联网、不调用 LLM |
| **静态类型** | **JSDoc + `tsc --allowJs --checkJs --noEmit`** 作为**可选开发期工具**，不产生运行时代码、不改变实现语言；贡献者可关闭 |
| **测试** | `node:test` + `node:assert` 零第三方依赖；AC-01～19 以可执行场景文件实现，先红后绿 |

**为何不选 C++（备选 B）**：标准状态同样合规，但没有官方 MCP SDK，需要自行实现 JSON-RPC 2.0 / stdio、UTF-8 处理与七语言格式化，并引入第三方 JSON / ICU 库；GPL-3.0 静态链接的 Corresponding Source 边界、依赖许可审计（NFR-008）、社区贡献门槛与 SDD/ATDD 的快速迭代节奏都显著变差。本项目是**文本规则引擎**，对 CPU 性能无特殊要求（NFR-003 ≤ 5 s），故工程性价比低。保留为回退选项。

**为何不选 C#**：ISO/IEC 23270:2018 已被 ISO 标记 **Withdrawn**，不满足用户「ISO 指定」的现行性要求。

### 3.6 后果

**正面**：官方 Tier 1 MCP SDK；原生 UTF-8 / JSON / 正则 / 文件系统；`Intl` 覆盖七语言格式化与拉丁语场景；`node:test` 让 ATDD 零依赖落地；同一份源码三平台运行；Markdown 可 diff；Corresponding Source 天然满足；贡献者门槛低。

**负面与缓解**：

| 代价 | 缓解 |
|------|------|
| 用户需预装 Node 20+ 运行时（v1 不发包管理器） | README 明确安装步骤；Release 附源码归档 + 校验和 + 运行说明；不引入发布流水线（FR-052） |
| 纯 JS 无编译期类型 | JSDoc + `tsc --checkJs --noEmit` + 严格 lint；schema 校验在边界处显式执行 |
| GC 语言性能 |  workload 为文本生成，NFR-003 的 5 s / 30 s 预算充裕 |
| Node 版本碎片 | CI 矩阵覆盖 20 / 22 / 24 LTS；最低版本写入 `engines` 与 CONTRIBUTING |
| 依赖 SDK 许可待审计 | M4 前完成 `THIRD_PARTY_NOTICES.md`；若冲突则退化为自实现最小 stdio 协议层（属实现细节，`plan.md` 记录） |

### 3.7 回退条件

出现下列任一情形时，按 `SPEC.md` **E-17 / A-09** 切换：① 用户明确要求改用 C++ 或其他现行 ISO 标准语言；② ISO/IEC 22275:2018 被撤销且无替代；③ Node 运行时无法覆盖 NFR-004 的目标平台。

回退时**只重做 `constitution.md`（如涉及原则）与 `plan.md`**，**不修改任何 FR / AC / SC 的业务语义**；全部验收契约保持有效。

## 4. ADR-003 · 语言策略：构建语言、输出语言体积与 LLM / 宿主边界

| 项 | 内容 |
|----|------|
| 状态 | **Accepted**（用户 2026-11-06 第四轮追问后选择「方案 A」） |
| 决策者 | 用户 |
| 影响 | 关闭 CL-11；维持 ADR-002 的单一实现语言；`../SPEC.md` 新增 FR-041 补注、FR-043 编码声明、AC-15 断言、A-10 / E-18；`../plan.md §11` 与 `../constitution.md §5` 预留准入门禁 |
| 不改变 | 任何 FR / AC / SC / P 的业务语义与编号；不新增实现语言；不引入运行期翻译 / LLM 依赖 |

### 4.1 背景与三问

用户第四轮追问：①「构建语言可以使用多语言吗？使用 ISO 及 GB 指定的多种语言，在语言的优势项目中使用特定语言。」②「输出语言种类过多是否会导致插件过大？」③「能否通过 LLM 或插件宿主达成多语言输出？」

三问指向同一分层问题：**构建语言（实现层） / 内部表示（Canonical ID） / 输出语言（数据与渲染层）**必须分开回答。本 ADR 只做技术决策；规格层只固化语言无关的约束（P-04）。

### 4.2 ISO 与 GB 标准状态核实（2026-11-06 联网）

| 体系 | 语言 / 标准 | 状态 |
|------|-------------|------|
| ISO/IEC | ECMAScript **22275:2018**（已选）、C++ **14882:2024**、C **9899:2024**、Ada **8652:2023**、Fortran **1539-1:2023**、COBOL **1989:2023**、Ruby **30170:2012**、Prolog **13211-1:1995**、Pascal **7185:1990**、Full BASIC **10279:1991** | JTC 1/SC 22 目录在版 |
| GB/T | **15272-1994** C（等同采用 ISO/IEC 9899:**1990**，即 C89）、**7591-1987** Pascal、**9542-1988** PL/1（等同 ISO 6160:1979）、**12856-1991** BASIC 子集（等效 ECMA-116） | 均「现行」，2022-01-10 复审结论「继续有效」 |
| GB 在研 | **20260533-T-469**《信息技术 程序设计语言 仓颉》 | 2026-01-28 下达、正在起草、周期 18 个月（华为 / 中国电子技术标准化研究院等）→ **未发布，不能作现行依据** |
| GB 强制 | **GB 18030-2022**《信息技术 中文编码字符集》 | 2023-08-01 实施、**全文强制**；实现级别 1 为所有中文信息处理产品最低要求 |

> 另有 GB/T 3057-1996 Fortran、GB/T 4092-2008 COBOL 见于国家标准平台相近标准清单，状态未单独复核，不纳入候选。**两个易错点**：①「GB 现行」≠「技术现行」——GB/T 15272 锁定 C89，而 ISO 现行为 C23（9899:2024），混用会造成「符合哪一版」的合规歧义；② 常被当作「最擅长该领域」的 Rust / Go / Python / TypeScript / Java **无现行 ISO 编程语言标准编号**，C# 的 ISO/IEC 23270:2018 已撤销（ADR-002 §3.4）。故 ISO/GB 过滤后，候选基本只剩 C / C++ / Ada / Fortran / COBOL 这批。

### 4.3 决策一：构建语言维持单一，不采用多语言

对「按优势域分工」逐项评估本项目（纯本地文本规则引擎，NFR-003 预算：周/日 ≤ 5 s、年 ≤ 30 s）：

| 候选优势域 | 常见选择 | 本项目是否需要 |
|------------|----------|----------------|
| 数值 / 营养计算 | Fortran、C++ | 否，四则运算 + 表查找，预算极充裕 |
| 并发 / 高吞吐 | Go、Rust（均无 ISO 号） | 否，单次本地 CLI、离线文本生成 |
| 形式化规则推理 | Prolog | 否，规则为确定性表驱动，非回溯搜索 |
| 高可靠 / 安全关键 | Ada | v1 非安全关键系统，收益不抵成本 |
| 中文生态 | 仓颉 | 标准在起草，不可作依据 |

混用多语言的实付代价：GPL-3.0 **Corresponding Source** 须覆盖每种语言的全部源码与构建脚本；CI 从「3 OS × 3 Node」变为「× N 工具链」；ATDD 场景跨语言维护；贡献者门槛抬高；NFR-008 依赖许可审计面扩大。

**结论**：v1 维持 **ADR-002 选定的 ECMAScript / ISO/IEC 22275:2018 单一主实现语言**；「多语言」诉求全部放到数据层（`locales/<tag>/strings.json`）与渲染层（可替换渲染后端）。ADR-002 §3.7 预留的是**整体切换**实现语言的回退，不是混用。规格层面 `SPEC.md` NFR-015 只要求「主实现 100% 为现行 ISO/IEC 标准化语言的人类可读源码」，本 ADR 不改该口径（引入 GB 语言需另行修订规格）。

### 4.4 预留：第二实现语言准入门禁（v1 默认关闭）

未来若确有可举证的能力缺口，须**全部**满足以下门禁才可新增 ADR 并启用第二实现语言：

| ID | 门禁 | 检查方式 |
|----|------|----------|
| **G-01** | 候选语言必须是**现行** ISO/IEC 或 GB 标准，写明标准号、版本与状态核实日期；在研 / 已撤销标准不合格 | 人工复核 + 标准平台链接入 ADR |
| **G-02** | 提交可度量基准，证明主实现语言无法满足 NFR-003（5 s / 30 s）或某项 MUST 能力；无基准不得引入 | CI 基准报告 |
| **G-03** | 只能经 stdio / JSON 端口接入，**不得进入核心域**，不得改变 Canonical ID 契约与 FR-044 语言无关性 | 架构评审 + 依赖方向扫描 |
| **G-04** | 全部语言的源码、构建与测试脚本随每个 Release 提供，满足 GPL-3.0 Corresponding Source 且许可兼容 | `license-scan` / 发布审计 |
| **G-05** | CI 矩阵扩展为新工具链 × 3 OS，跑同一组 AC-01～19 且结果一致 | `matrix` job |
| **G-06** | **默认关闭**：须用户书面确认 + 新增 ADR + 重做 `plan.md`，且**不改任何 FR / AC / SC 业务语义** | 用户确认记录 + 规格 diff 检查 |

> 对应 `SPEC.md` **A-10 / E-18**、`plan.md §11` 的 `polyglot-gate`、`constitution.md §5` 门禁清单。门禁未通过时的默认动作是「维持单语言」，而不是临时豁免。

### 4.5 决策二：输出语言种类不构成插件体积膨胀

前提是「语言 = 纯键值数据」而非「语言 = 翻译模型」。按 300 条界面键 + 550 条菜名/食材名、每条含键名约 100/60 字节估算：

| 项 | 体积 |
|----|------|
| 7 个内置语言包（未压缩） | **≈ 0.42 MiB**（界面 205 KiB + 菜名食材 226 KiB） |
| 同上 gzip | ≈ 151 KiB |
| 扩到 30 种语言 | ≈ 1.8 MiB |
| opus-mt en-zh 离线模型 | 425 MiB（约为语言包的 **1011 倍**） |
| NLLB-200-distilled-600M | 600 MiB～2.4 GB（依精度 / 量化，约 **1427 倍**） |
| ONNX Runtime wasm | ≈ 74 MiB |

架构上现有设计已避免膨胀：`locales/<tag>/strings.json` 外置、`locales/_schema/keys.json` 校验键集、核心只存 Canonical ID、日期/数字/单位交给 Node 自带 `Intl`（默认 **full-icu**，数据由运行时提供，**增量 0 字节**）、语言包可独立于 Release 分发且按需加载。

**三个真正会撑大发布物的做法**：随包附带翻译模型 / ONNX Runtime；把每种语言的菜谱**全文**各存一份（应只存 Canonical ID）；自行再打包一份 ICU 数据。另：拉丁语 `la` 的 CLDR / ICU 覆盖较薄，需自定义最小复数与日期规则 + 规范译名表（FR-043 已允许「译名 + 学名/原文」并列）——属**术语质量**问题，不是体积问题。

### 4.6 决策三：LLM 与宿主只能作可替换渲染器

| 路径 | 判定 | 理由 |
|------|------|------|
| LLM 运行时翻译全部输出 | ❌ **不可** | 撞 FR-041（运行期翻译 MUST NOT 依赖在线服务或 LLM）、FR-051（核心不依赖 LLM）、FR-047/048（身体数据零上传、逐次同意、PIPL/GDPR）、NFR-001 离线优先、NFR-009 供应商中立；非确定性输出还会破坏 AC-15 / SC-011 的键集与快照断言 |
| **LLM 开发期生成候选译文** | ✅ **推荐** | 贡献者用 LLM 产出新语言包的候选键值 → 人工（母语 / 术语）审校 → 以静态 UTF-8 文件提交入库并标注来源与审校者。运行期完全不调用，Corresponding Source 齐备，ATDD 仍可对确定字符串断言。**把 LLM 当翻译作者工具，而非运行时组件**（已固化为 FR-041 补注） |
| 宿主提供 locale 提示 / 字体 / `Intl` | ✅ 可 | 但 FR-045 明禁静默推断；宿主语言只能作**默认候选且必须用户可覆盖**，核心 CLI 必须能脱离宿主独立运行 |
| 宿主对最终 Markdown 做后处理翻译 | ⚠️ 可选旁路 | 仅显式开启；断言必须基于 Canonical ID 与结构，不能基于渲染后的自然语句 |

底层保险：`FR-044 / SC-011` 规定切换语言不改变营养数值、去重指纹、台账与计划语义，故渲染器可替换而规则引擎不受影响。

### 4.7 编码合规补强

`SPEC.md` FR-043 追加：面向中国市场发行时，中文输出的汉字字符处理 **MUST** 满足 **GB 18030-2022 实现级别 1**；落盘编码仍统一 UTF-8。AC-15 增一条中文编码断言，由 CI 校验。GB 18030-2022 是全文强制性国家标准，适用于具备中文信息处理与交换功能的技术类产品（含机器翻译类软件产品），实现级别 1 为最低要求；「符合」在此指所用汉字处于该级别覆盖范围，而非改用 GB 18030 作为文件编码。

### 4.8 后果

**正面**：构建层与 CI 保持简单；Corresponding Source 边界清晰；语言包可社区共建；离线 / 隐私 / ATDD 确定性不受影响；v1 发布物保持在 KiB 量级。

**负面与缓解**：

| 代价 | 缓解 |
|------|------|
| 单语言无法利用他语言生态优势 | G-01～G-06 留出可举证、可回退的启用路径；本项目当前无此类缺口 |
| 七语言（尤其拉丁语）术语需人工审校 | 开发期 LLM 候选译文 + 母语审校 + 「译名 + 学名/原文」并列（FR-043 / E-12 / R-06） |
| 新增语言包需维护键集一致性 | `rr locales --verify` + CI 键集校验（SC-011） |
| GB 18030-2022 增加一项 CI 校验 | 纳入 `lint-typecheck` / 语言包检查，纯静态脚本，无运行期依赖 |

### 4.9 回退条件

① 用户明确撤销方案 A；② G-01～G-06 全通过且用户书面确认启用第二实现语言；③ GB 18030-2022 或 ISO/IEC 22275:2018 状态变更（后者按 ADR-002 §3.7 / SPEC E-17 处理）。任一情形均新增 ADR 并重做 `plan.md`，**不改任何 FR / AC / SC 业务语义**。

## 5. 由决策引出的新增约束（摘要）

1. **i18n 是架构约束，不是翻译功能**：规则引擎只处理 Canonical ID；语言包承载全部人可读字符串；翻译不得依赖在线服务或 LLM。
2. **切换语言不改变任何数值**：营养计算、去重指纹、台账、时间线护栏与计划语义必须与语言无关（FR-044）。
3. **区域策略可追溯**：默认按声明的国籍 → 居住地解析，用户覆盖优先，未匹配显式回退；禁止通过 IP / 定位 / 静默推断（FR-045/046）。地区码按 ISO 3166-1，中国香港 / 中国澳门 / 中国台湾为中国的地区级选项。
4. **历法可插拔**：精确节气流程只在解析为 `solar-terms` 时适用；通用季节历同等遵守「年计划刷新、下层只读、失败 FALLBACK」。
5. **示例数据零真实个人信息**：两份合成档案，标注虚构性；CI 静态扫描防止 `diet-plan/` 数据误入库。
6. **许可边界**：代码 GPL-3.0；第三方数据 Unlicense / CC0 / 用户自建；不得复制受版权保护的指南原文或图表。
7. **标准化实现语言（D-11）**：主实现为现行 ISO/IEC 标准化语言的人类可修改源码；机器语言 / ISA 绑定代码不得作为主实现；每个 Release 附 Corresponding Source（NFR-015 / P-16 / AC-19 / SC-015）。
8. **规格与选型分离**：`SPEC.md` 只固化语言无关的强制约束；具体语言、运行时、目录、接口一律写在 `plan.md` 与本 ADR（P-04）。
9. **语言策略（D-12 / ADR-003）**：维持单一主实现语言；多语言由语言包与可替换渲染器承载；第二实现语言须过 G-01～G-06 门禁且 v1 默认关闭；运行期不得用 LLM / 在线翻译，开发期 LLM 候选译文须人工审校入库；中文输出满足 GB 18030-2022 实现级别 1。
10. **M2 边界**：`tasks.md` 只拆任务不写实现；每个任务关联 FR / AC / SC 并遵循红→绿顺序。
